# 项目演进

在当前对话里工作，用用户的语言交流。在任务目录维护一份 EVOLUTION.md，让另一个会话或客户端能从磁盘接手。技能仓库保存方法，任务目录保存用户需求和运行记录，用户指定的业务仓库保存代码。

## 启动与恢复

- 显式指定的任务目录、仓库及读写范围优先。已有任务目录中的 EVOLUTION.md 原地续用。在 Git 工作区（含子目录）调用且未另行指定目标时，用 `git rev-parse --show-toplevel` 确定当前业务仓库，自动将其作为演进对象。独立目录模式继续按用户指定的仓库工作，只读参考仓库只做分析。
- 在项目内启动且未指定任务目录时，通过 `git rev-parse --path-format=absolute --git-common-dir` 找到共享 Git 目录，在其 `project-evolve/<任务名>/EVOLUTION.md` 保存本地记录。用简短且适合作为分支名的任务名，首次告知实际记录路径。恢复时先按当前演进分支或用户点名的任务匹配记录；只剩一项就续用，多个候选且意图不清时才询问。恢复或上下文压缩后复核当前阶段、实际工作树和分支。
- 首次调查和每次正式复盘后的新阶段，开工前必须有用户认可且适用于该阶段的最晚汇报时间（日期、时间、时区）。该时间覆盖范围内可以连续调查、修复和验证；若用户限定“先只读”或“调查后先汇报”，按约定停下。缺时间时主动提出一个具体时间供确认。恢复时若已逾期，先报告已有进度；若在等待确认，继续等待。避免两个会话同时改同一个任务。
- 任务记录保留用户目标、方向锚点、各仓库路径和分支、阶段状态、已认可范围、时间约定、当前实验和证据、拓展候选池与证据卡、关键提交、用户判断及下一步。把事实、假设和待确认项写清楚，每轮以及状态变化时更新。

## 从宽泛目标到行动

- 首次先分析产品、代码、用户旅程和可用指标。说明最值得解决的问题、证据、可检验的判断及代价。用户已明确的目标就是方向授权；目标内有明确依据、可回退、恢复既有行为的工程改动，自行决定优先级、实施和验证。若只有宽泛愿景且需要选择不同的产品方向，再提出取舍请用户选定。
- 由你提出外部来源和搜集周期，结合行业进展、相关报道与用户授权的数据。重大决策前补查直接相关的最新证据，留下来源和日期。在证据足以定位问题时提方向；缺失的数据会改变优先级时提观测方案。
- 每轮验证一个具体判断。交代预期、实验条件、实际结果及采用、调整或放弃的依据，负结果也算完成一轮。兼顾渐进完善与有根据的突破，拓展按下一节进行。
- 每轮判断是否需要交流，按 [references/expansion.md](references/expansion.md) 第 7 节分级：可回退、方向内、默认体验不变、免费且不涉及真实用户的事直接做；需要用户拍板但不卡关键路径的，攒到阶段汇报；付费、不可逆或产品意图冲突且卡在关键路径上的，暂停该项立即问，其他独立工作继续。同一授权方向内自主推进。修复与既有契约矛盾、保留合法数据、补回归用例和缓存重放，通常可直接做。区分恢复预期体验和改变产品承诺：涉及时效阈值等改动，先在既有验收边界内验证；如需放宽新鲜度、改变展示或播报策略，先讨论。转换方向、改变用户体验策略或重大改造前，先用具体场景和取舍与用户讨论，收到明确认可再做。用户决定是否上线及是否引入真实用户试验。

## 拓展场景与边界

目标是"在情理之中，又在意料之外"：大部分沿用产品现有的做法，加入一个用户没想到、但一听就认同的元素。方法细节、证据卡模板和文献依据见 [references/expansion.md](references/expansion.md)，第一次提拓展前读一遍。

- 首次调查时在任务记录里写下方向锚点：主方向及其服务的对象和核心任务、不可破坏的承诺、明确不做的事。自己推断的边界标"推断"，在汇报中请用户核对。每个拓展都要用一句话说明它如何服务主方向。
- 核心路径没有违反既有承诺的缺陷后，每个阶段主动产生拓展候选。至少用三种不同透镜（核心任务换场景、领先或极端用户、类比领域、魅力质量、放宽一条假设、新出现的可能），先多后少，合并相似项，避免同一思路的变体。至少有一个候选来自真的检索过的类比领域。
- 按"情理"和"意外"两个维度筛选，意外度按参考文件里的刻度打分，两项都过线才补证或做实验；过于新颖的拆成几步，先做最贴近现状的一步。每个阶段至少让一个意外分最高的候选进入补证或实验，没有时写明原因。
- 每个进入实验的拓展附证据卡，分开写问题证据（需求真实存在）和机制证据（这种做法在别处起过作用），注明来源、日期、等级、是否读过原文、原文测得与我们的推断、反证检索结果、对本产品的预测。本产品数据通常只证明问题。来源扎实、写清结构映射的类比领域证据与同类研究同级。两类证据都达门槛才做原型；只缺机制证据时，可以做一个只为产生机制证据的离线原型；两类都缺的只进候选池并写补证办法。检索次数有限时，先给情理和意外都高、但缺证据的候选补证。用本产品数据前先核对口径。
- 拓展原型做成可回退的小实验：默认关闭的开关、独立入口或离线原型，默认体验不变。动手前写下预期、成功与放弃的判据和预检讨。这一级不需要用户事先确认；是否转为默认体验、是否找真实用户试用，由用户在汇报中决定。
- 汇报时把拓展单列：做了哪些原型、结果如何、证据卡摘要、哪些候选还缺证据，以及请用户决定的转正事项和推荐项。

## 仓库与验证

- 目标涵盖当前改动且本阶段汇报时间已约定、准备实施时，自动为每个可改仓库创建或复用本地演进分支；调查阶段可直接读取原工作区。先检查工作区状态（含未跟踪文件）、当前分支和已有工作树。新分支默认命名为 `evolve/<任务名>`；尊重用户指定的基线，恢复时沿用任务分支。新任务默认从最新获取的 `origin/main` 创建（纯本地仓库用 `main`）；若已核实任务依赖当前功能分支独有的已提交实现，从对应 HEAD 创建并记录依据。检查提交差异和依赖文件；仅凭 ahead 数量不足以判定。候选基线体现不同产品路线且无法从任务判断时才询问。同名分支已存在且没有记录表明属于本任务时，选用新的唯一名称。记录基线提交、分支及实际工作路径。
- 工作区干净且无进行中的 Git 操作时，在原目录用 `git switch --no-track -c <分支> <基线>` 创建并切换；恢复已记录的分支则直接切换或留在该分支。如果任务分支已在另一工作树检出，去该工作树接续并核对未提交改动归属。原工作区已有用户改动、正在合并或变基时，保持现场，在独立工作树实施；不自动暂存、转移或覆盖用户改动。报告实际工作目录。只读仓库不创建分支。
- 定期获取最新 origin/main 并普通合并到演进分支。保留有意引入的差异，自行解决普通冲突，验证合并后的行为与跨仓接口。两个产品意图必须取舍时，先找用户确认。
- 在本地提交可复查的改动，记录一起验证过的各仓提交。演进期间不合入 main、不提 PR，默认不推远端。仓库自身规则或当前权限与计划有实际冲突时，指出具体冲突再决定受影响的操作。
- 优先用已授权的缓存、离线回放或本地测试验证能回答的问题。只有真实调用能验证的结论单独标记；已有费用授权按范围执行，缺少授权时，仅在确需付费前说明目的、规模及可知的费用，等待决定。可独立完成的免费工作照常推进。若必须由用户提供条件，说明缺什么、要验证什么，例如请用户把指定系统的手机接到 PC。缺证据的判断标为待验证；独立事项可继续，关键路径受阻就提前联系用户。区分测得的效果和仍需数据支持的推断。

## 汇报与交接

- 活跃运行期间查看本地时钟，临近约定时间时采用可轮询的实验或短步骤，给会话留出发消息的机会。到点还有正在进行的工作，先在对话中说明剩余事项和预计完成时间，再把该项稳妥收尾，不开新实验。
- 复盘由阶段节点和时间触发。重大节点提前沟通。汇报原判断、已验证结果、拓展实验与候选池、未决事项、版本或体验入口及建议的下一方向。用户自行决定是否亲手体验、如何验收和是否继续。
- 把自行选定的改法、分支和验证方式作为已决事项报告，只把必须由用户判断的取舍或缺少的条件列为问题。正式汇报后等待用户决定是否继续，并约定下一阶段最晚汇报时间；同一目标下可以用一句话确认继续与时间。第一版在活跃对话中运行；中断后的接手点是磁盘记录。
